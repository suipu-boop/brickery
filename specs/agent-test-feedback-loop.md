# 测试 agent 反馈闭环（本地修 → 工坊产出 → 网页同步）

> 状态：待确认
> 日期：2026-08-21
> 背景：积木工坊 App 已验证可组装产出 agent 安装包。下一步进入真实使用阶段：用户安装测试 agent，发现问题反馈，Marvis 修改，验证后同步网页端。

## 1. 目标

打通「真实使用 → 发现问题 → 修复 → 重新产出 → 网页同步」的完整迭代闭环，让积木生态在真实使用中打磨。

## 2. 角色与职责

| 角色 | 职责 |
|---|---|
| 用户 | 安装测试 agent（从工坊产出）；实际试用；反馈不能用/不如意的地方 |
| Marvis | 定位并修改底座/积木块代码；同步 base 缓存；按确认提交推送；同步网页端市场源与站点 |

## 3. 闭环流程（每轮迭代）

1. **用户安装测试 agent**：用积木工坊产出 agent 安装包，装到系统（本机或目标机）
2. **用户试用**：正常使用，记录问题点
3. **反馈**：用户把问题（报错/行为不符/缺能力）发给 Marvis
4. **定位修改**：Marvis 分析问题根因，改动 brickery 仓库对应代码（底座 runtime / 积木块定义 / 配置）
   - 核心改动前先落盘 `specs/` 设计文档供审阅（用户已确认的偏好）
5. **同步运行中的 agent（关键）**：除网页端外，把改动**直接同步到用户正在运行的测试 agent 应用副本**：
   - 定位 agent 安装位置（如 /Applications/xxx.app 或桌面产物）
   - 同步 app 内 `Contents/Resources/brickery-runtime/`（底座代码）与积木定义（bricks / skills.json）
   - 用户重启 agent 即可继续测试，无需重新产出安装包
   - **硬约束：仓库为真源**——凡是同步到运行中 agent 副本的改动，**必须同时**落到 brickery 仓库（GitHub），禁止只改副本不改仓库；副本只是仓库代码的运行实例
6. **同步 base 缓存**：改动同步到 `~/.brickery/base/brickery`，工坊产出时读取最新代码（后续产出新包也用得上）
7. **重装/重启复测**：用户重启（或必要时重装）测试，确认问题解决；未解决继续回到 4
8. **网页端同步**（问题确认解决后）：
   - 积木块内容变更 → 更新市场源 `suipu-boop/shadeling-bricks` 的 `skills/<id>/<version>.json` 与 `index.json`
   - 网页站点文案/功能变更 → 改 `site/index.html`，subtree 推送 gh-pages
9. **提交推送**：改动提示未提交，用户确认「提交推送」后 Marvis 执行（用户偏好）

> 说明：第 5 步是「快速迭代通道」（改运行中副本，重启即测）；第 6 步保证工坊产出链路上代码一致；两条通道并存，最终以仓库代码为准。

## 4. 修改边界与落点

| 问题类型 | 修改落点 |
|---|---|
| 底座行为（聊天/记忆/调用） | brickery 仓库 runtime 代码（app 内嵌） |
| 单个积木块行为/提示词 | 积木定义（skills JSON / 市场源仓库） |
| 积木工坊 App 本身 | brickery 仓库 + 重新 build_workbench_app.sh |
| 网页市场/展示 | site/index.html + shadeling-bricks 市场源 |
| 正在运行的测试 agent | 直接改 app 副本内 `brickery-runtime` 与积木定义（快速通道） |

## 5. 注意事项

- 每次迭代以「一个明确问题」为单位，避免一次改太多难定位
- 修改后先同步 base 缓存再提示用户产出，避免用户产出到旧代码
- 市场源版本号：积木内容变更建议升版本（如 1.0.0 → 1.0.1），网页端按 index.json 展示最新
- 无法本地复现的问题，用户提供报错文本/截图即可定位
